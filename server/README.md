# DON'T TAP THAT — weekly leaderboard backend

Serverless API for the optional weekly leaderboard and friend groups:
**API Gateway (HTTP API) → Lambda (Node 22, arm64) → DynamoDB (on demand)**.
No accounts: a device is a random UUID plus a secret key generated by the app. The
server remembers a hash of the first key it sees per device (trust on first use).

At this scale it costs cents per month. Throttling is set to 20 req/s (burst 40).
The account's Lambda concurrency quota (10) is a second ceiling.

## API

| Method | Path | Purpose |
|---|---|---|
| POST | `/v1/scores` | Submit `{deviceId, deviceKey, name, weekId, score, rounds[]}`; returns rank/total |
| GET | `/v1/weeks/{weekId}/leaderboard?limit=&deviceId=` | Top entries (+ your rank if `deviceId` given) |
| POST | `/v1/groups` | Create a friend group; returns a 6-character code |
| POST | `/v1/groups/{code}/join` | Join a group (max 50 members) |
| GET | `/v1/groups/{code}/weeks/{weekId}` | Group leaderboard |
| POST | `/v1/delete` | Delete everything for the device (privacy) |
| GET | `/v1/health` | Liveness |

Responses never include device ids. Ties share a rank (1, 2, 2, 4).

## How scores are checked (and what that does not guarantee)

The game is seeded per week, so the server **replays** the week's sequence using the
game's own `weekly.js`, `challenges.js` and `adaptive.js` (copied in by `build.js`, with a
test that fails if they drift). A submitted run must have exactly `score` rounds, each
with a human-possible reaction time (>= 80 ms) within that round's real time limit, and
wait-it-out rounds must take about the full limit. Only the current week (or last week for
6 hours after the reset) accepts scores.

This stops made-up scores and casual tampering. It is **not proof**: the game runs on
the player's device, so a determined cheater can forge a plausible run.

Names: letters, digits, space, `_`, `-`, max 14, filtered for profanity (incl. leetspeak);
filtered names become `PlayerNNNN`. The word list in `src/validate.js` is a starting point;
extend it as needed. Some innocent names (e.g. "Sussex") are caught by the strict filter.

## Data and retention (DynamoDB, one table)

Weekly scores expire after 70 days, groups after 365 days (DynamoDB TTL). `POST /v1/delete`
removes a device's key, scores and memberships (found via the `byDevice` index). Group
records store no owner id.

## Develop

```bash
cd server
npm test            # 46 tests: validation, plausibility, API flows, store contract, bundle
npm run build       # assembles dist/ (server code + the game's logic files)
```

The in-memory store and the DynamoDB store implement one contract and run the same
tests (the DynamoDB one against a fake that paginates and returns unprocessed batches).
`scripts/leaderboard.test.js` in the app repo runs the real client against the real
handler end to end.

## Deploy (you run these; nothing here deploys itself)

Prerequisites: AWS profile `corey` (IAM admin). The Terraform state backend reuses the
existing `vantry-tfstate-981207388221` bucket and `vantry-tfstate-lock` table.

```bash
cd server
npm test && npm run build
cd terraform
AWS_PROFILE=corey terraform init
AWS_PROFILE=corey terraform plan      # review: expect ~13 resources, no changes elsewhere
AWS_PROFILE=corey terraform apply
AWS_PROFILE=corey terraform output api_url
```

Then:

1. Put the `api_url` value in `js/leaderboard-config.js` (`apiBase`).
2. **Before shipping that build**, update the App Store privacy answers (see below) and
   deploy the updated `privacy.html`.
3. Smoke test: `curl "$(terraform output -raw api_url)/v1/health"`.

`terraform destroy` removes everything (the table has no deletion protection; the data
is disposable). Do not raise `max_concurrency` without a Lambda quota increase: the
account quota is 10 and AWS requires 10 to stay unreserved.

## App Store privacy answers when the leaderboard is enabled

"Data Not Collected" stops being accurate. Declare, for the leaderboard only:
- **User Content / Gameplay Content**: weekly score and reaction times. App functionality,
  not used for tracking.
- **Identifiers / User ID**: the random anonymous ID. App functionality, not linked to
  identity, not used for tracking.
- **Other User Content or Contact Info → Name**: the player-chosen display name (it is
  free-text-ish). Review with Apple's definitions; declaring it is the safe choice.

Also revisit the age rating and Kids/child-audience implications before enabling: the app
is for all ages and has no age gate, and the leaderboard shows user-chosen names.
